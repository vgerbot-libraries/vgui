vgui provides native GPUI integration and WebAssembly-specific support with distinct entry points. The maintained counter demonstrates both targets, while native and browser behavior remain separate verification concerns.

## Current capabilities and verification

| Path | What is available | What it does not prove |
| --- | --- | --- |
| Native counter | The maintained dual-target counter uses `gpui_platform::application()` and can be run with `cargo run -p vgui --example counter`. | The documentation does not claim that native window display or button interaction was verified. |
| WebAssembly target | The same counter uses `single_threaded_web()`, `run_embedded`, `web_init()`, and browser keyboard interception. The website build generates its precompiled WASM assets. | Building WASM alone does not exercise browser rendering or input. |
| Browser demo | The [counter page](../examples/counter/) pairs the real read-only source with a live precompiled WASM preview. The website browser test covers canvas rendering and Increment interaction. | This does not verify native UI interaction or every browser platform integration. |

## Native applications

The [Quick Start](../quick-start/) follows the native model:

1. Create the current platform's GPUI application.
2. Run the native event loop.
3. Open a GPUI window.
4. Mount the vgui root view into that window.

The markup still produces GPUI elements. Elements do not become browser DOM nodes, and window behavior comes from the native GPUI backend.

## What changes in a browser

A browser host must address concerns that a native window handles differently:

- **Entry point and lifetime:** WASM startup is non-blocking and uses the web platform rather than the native `application().run` path shown in the Quick Start.
- **Canvas sizing:** the host page and canvas determine the available viewport. A fixed native window size is not a responsive browser layout.
- **Keyboard behavior:** browser defaults such as Tab navigation and Space scrolling can conflict with canvas input. vgui exposes `intercept_keyboard_events()` to install bubbling-phase keyboard listeners for a browser canvas; on native targets it is a no-op.
- **Input and platform behavior:** text input, IME, clipboard, accessibility, and other OS integrations need their own browser validation.

The counter's WASM `start()` combines `web_init()`, keyboard interception, and `run_embedded` to provide the complete startup path used by the preview.

## Verification boundary

The counter page displays the maintained source and loads precompiled WASM assets generated by the website build. The website browser test covers canvas rendering and clicking Increment. These checks do not verify native window display or native button interaction.

Treat native compilation, native interaction, WASM compilation, browser rendering, and browser interaction as separate checks. Browser coverage of the counter does not by itself validate text input, IME, clipboard, accessibility, or other integrations.

For build or display problems, continue to [Compatibility & Troubleshooting](../compatibility-troubleshooting/).
